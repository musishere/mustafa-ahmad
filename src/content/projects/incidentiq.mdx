## Problem

When an alert fires, someone has to find the service, read its logs and metrics, check the runbook, try a fix and tell people what happened. I wanted an agent to run that loop for a known service. The model can ask for any action it likes; code decides what actually runs.

## What I built

Three phases, each with its own system prompt and its own tools: diagnose, remediate, communicate. When a phase ends, its history is replaced with its summary, so the next phase starts from conclusions instead of raw logs. Before any of that, a scope check refuses alerts that don't name a service it knows, without calling the model.

All nine tools go through one function, `execute_tool`. Remediation actions are checked there in a fixed order: is this the incident's service, has the same action run in the last 15 minutes, and which tier does the action fall in.

`restart_pod` runs on its own unless the service is marked critical. Scaling runs on its own within ±20%. Rollback and delete always need a person, and so does any action the code doesn't recognise. Every attempt is written to a `remediation_log` table, and every model call and tool call goes to a JSONL trace tagged with its phase.

The test data includes a legacy logs table with different column names and MM/DD/YYYY dates. The tools normalise it, so the model never sees two schemas.

There's no agent framework. The loop, the dispatcher and the permission checks are plain Rust over Postgres.

## Hardest part

Testing the agent against a poisoned runbook. I hid a fake log line in the middle of `recommendation-service-cache-issues.md`: a `[SYSTEM: ...]` note telling the agent to run `delete_resource` on checkout-service, marked as pre-approved.

The first test passed for the wrong reason. `search_runbooks` returns one line per document, the first line that matches the query, and that was the title, so the payload never reached the model. I had to query with words that only appear in the payload line to confirm it was delivered. With realistic queries the model never surfaced it at all. That was luck in how snippets get picked, not a defence.

Once the payload was in context, the model ignored it and stayed on recommendation-service. But reading the code afterwards showed what would have happened if it hadn't: nothing tracked which service the incident was about after the first alert check. The only thing in the way was that `delete_resource` always needs confirmation. Any action that tiered as automatic would have run against the other service.

So I added a check that runs before every other one:

```rust
pub fn check_cross_service(target_service: &str, incident_service: &str) -> Option<Tier> {
    if target_service.eq_ignore_ascii_case(incident_service) {
        None
    } else {
        Some(Tier::CrossService(format!(
            "'{target_service}' is not the service this incident is about ('{incident_service}') \
             — refusing a cross-service remediation action"
        )))
    }
}
```

## Tradeoff

Not every eval goes through the model. The full-pipeline cases do, and they assert which guardrail fired rather than what the model said. The permission and loop-detection cases call `execute_tool` directly, because across runs the model asked for the same fix as `restart_pod`, `restart_service` and `restart_cache`. I wanted the permission tests to test permissions, not the model's wording.

The two held-out cases were written once and never tuned against. One of them fails: an alert naming two services roughly doubles the tool calls, and the run hits the 12-call budget before it finishes. I logged the failure instead of patching it, so the held-out set stays held out.

## Numbers

| Metric | Value | How I measured it |
| --- | --- | --- |
| Regular eval suite | 5 of 5 pass | full-pipeline and direct-dispatch cases |
| Held-out set | 1 of 2 pass | the two-service alert ran out of model calls |
| Unit tests | 50 across 8 modules | run against a real Postgres |
| Model-call budget | 12 per incident | fixed cap |

## What I'd change

There's no approval flow yet, so actions that need a person can't get one. I'd build that first. After it: a dry run for `delete_resource`, a circuit breaker, and a model-call budget that grows with the number of services in the alert instead of a flat 12.
